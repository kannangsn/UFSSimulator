# Adding UFS 4.1 / UFS 5.0 Support to MQSim

**Architecture gap analysis and a day-by-day implementation plan**

- Repository: MQSim (SSD simulator)
- Baseline reference: JEDEC JESD220 (UFS 1.0/1.1 base architecture)
- Feature deltas confirmed via JEDEC/vendor sources for UFS 4.1 and UFS 5.0 (JESD220H, published February 2026)
- Prepared: 2026-07-15

## Scope decisions

- **Fidelity target: performance-simulation fidelity.** Model UFS's timing-relevant behavior (queue/doorbell semantics, UPIU header overhead, HS-Gear bandwidth/latency) at the same abstraction level MQSim already uses for NVMe/SATA. Full SCSI CDB parsing, task management functions, query requests, and the power-mode state machine are explicitly out of scope.
- **Versioning: sequential milestones.** A working UFS 4.1 baseline (including MCQ) first, then UFS 5.0 as a smaller follow-on delta (HS-Gear 6 bandwidth constants) on the same code path.
- **Timeline: ~18 working days** (15-20 day target band), not necessarily consecutive.

---

## 1. Architecture Summary

MQSim's host-interface layer is cleanly separated from flash-level simulation via `Host_Interface_Base`, which every protocol (currently NVMe and SATA) subclasses. The base class owns a `PCIe_Switch` transport handle, a `Data_Cache_Manager_Base`, and two protocol-supplied collaborators: an `Input_Stream_Manager_Base` (segments `User_Request`s into `NVM_Transaction_Flash_RD/WR` objects) and a `Request_Fetch_Unit_Base` (drives simulated DMA of command/data payloads over the link).

NVMe models up to 8 SQ/CQ pairs via fixed MMIO doorbell addresses, with priority-weighted arbitration (URGENT/HIGH/MEDIUM/LOW). SATA is structurally a single-stream instance of the same NVMe-style queue-pair mechanics. It reuses NVMe's `Submission_Queue_Entry` struct and opcode constants directly. There is no distinct SATA transport or PHY model. Both share the same `PCIe_Link` / `PCIe_Root_Complex` / `PCIe_Switch` transport, which branches on a two-value `HostInterface_Types` enum.

The flash-level stack (`Address_Mapping_Unit_*`, `FTL`, `GC_and_WL_Unit_*`, `Flash_Block_Manager_*`, the ONFI/NVM-chip backend, and the `NVM_Transaction_Flash_RD/WR` / `User_Request` types) takes only generic stream-id, LPA, and PPA parameters with zero NVMe/SATA-specific logic. **Adding UFS is purely a host-interface and transport-layer addition. No flash-simulation code needs to change.**

## 2. UFS Protocol Model (from JESD220 baseline)

UFS uses a layered model: Application → UFS Transport Protocol (UTP, exchanges UPIU packets) → UIC (MIPI UniPro link layer + M-PHY physical layer). Commands follow the SCSI Architecture Model (SAM-5): a client-server / request-response model where the Initiator (host) addresses a Logical Unit (LUN) inside the Target (UFS device).

- **UPIU packets**: fixed 32-byte basic header (Transaction Type, Flags, LUN, Task Tag, Command-Set Type, Query Function, Response, Status, EHS/Data-Segment lengths) followed by a transaction-specific area. Command UPIU carries a 16-byte CDB. Response UPIU carries SCSI status and sense data.
- **Task Tag**: generated by the Initiator, uniquely identifies a task end to end. This is UFS's analogue of an NVMe command ID or SQE slot index.
- **Single command queue** in legacy/SDB mode, task-tag-addressed, up to 32 outstanding slots, one doorbell bitmap register (UTRLDBR) rather than NVMe's per-queue head/tail registers.
- **Task Management Functions** (Abort Task, Abort Task Set, Clear Task Set, Logical Unit Reset, Query Task[Set]). Out of scope at performance-fidelity level, noted for completeness.
- **Power mode state machine** (Active / Idle / Pre-Active / Sleep / Pre-Sleep / PowerDown / Pre-PowerDown via START_STOP_UNIT). Out of scope at performance-fidelity level.
- **Query Requests** (descriptor/attribute/flag read-write). Out of scope at performance-fidelity level.

### UFS 4.0 / 4.1 deltas (confirmed via JEDEC/vendor sources)

- **Multi-Circular Queue (MCQ)**: up to 32 submission and 32 completion queues, architecturally close to NVMe's multi-queue model. That makes NVMe the best available reference implementation inside MQSim.
- **UFS 4.1**: WriteBooster buffer resize/partial flush, host-initiated defragmentation, RPMB authentication, permanently-bootable LUs. These are feature and stat-level additions (means some of them mainly surface as new status fields or attributes you can query), not timing-critical.
- **Link speed**: HS-Gear 5, up to 23.2 Gb/s per lane (46.4 Gb/s per device, 2 lanes).

### UFS 5.0 deltas

- **HS-Gear 6** (M-PHY 6.0): up to 46.6 Gb/s per lane, about 10.8 GB/s effective sequential throughput over 2 lanes. Roughly 1.6x UFS 4.x bandwidth.
- Integrated link equalization, isolated PHY power rail, and inline hashing are signal-integrity and security features. They have no timing-model relevance at MQSim's abstraction level. Explicitly out of scope, documented as such rather than modeled.
- Spec published as JESD220H / JESD223G (UFSHCI 5.0), February 2026. Maintains hardware compatibility with UFS 4.x, meaning no expected queue-depth/register-layout break from 4.1.

## 3. Concrete Gap Analysis

| Area | Files | Change |
|---|---|---|
| **Protocol enum & constants** | `src/ssd/Host_Interface_Defs.h` | Add `UFS` to `HostInterface_Types` enum. Add UFS opcode/register constants in their own address block. Must **not** alias NVMe's registers the way SATA does, since UFS needs genuinely distinct UTRD/task-tag semantics. |
| **New host interface** | new: `src/ssd/Host_Interface_UFS.h/.cpp` | Subclass `Host_Interface_Base`, following the NVMe/SATA pattern. New command-descriptor struct (UTRD-like, not a reused `Submission_Queue_Entry`). Single UTRLDBR bitmap doorbell for the baseline. Per-queue doorbells once MCQ is added. |
| **Stream/fetch collaborators** | new: `Input_Stream_UFS`, `Request_Fetch_Unit_UFS` | Reuse `segment_user_request` from the existing NVMe/SATA pattern. This part is protocol-neutral and needs no new logic beyond connecting the pieces. |
| **Transport dispatch** | `src/host/PCIe_Root_Complex.cpp` (~L9-71) | Add a UFS branch to the `SSD_device_type` switch. Add a `UFS_HBA` (SATA-style, separate adapter) or extend `IO_Flow_Base` (NVMe-style, baked into the shared flow base). SATA's approach of reusing NVMe structs outright will not work for UFS's distinct UPIU/task-tag model. |
| **Config integration (5+ sites)** | `src/exec/Device_Parameter_Set.cpp/.h`, `src/exec/SSD_Device.cpp` (~L200-262, 351-365), `src/exec/Host_System.cpp` (L17-21, 36-43, 83-86, 94-96, 116-130), `src/utils/Logical_Address_Partitioning_Unit.cpp` | Every site does an exhaustive switch/if over the closed 2-value enum. Each needs a third case. Several fall through silently on an unmatched case instead of reporting error, so a missed site fails quietly rather than loudly. Check each one manually rather than trusting the compiler to catch it. |
| **Build system** | `MQSim.vcxproj` / `MQSim.vcxproj.filters` | Mechanical copy-paste of the NVMe/SATA `<ClCompile>`/`<ClInclude>` entries. The Makefile globs `src/ssd/*.cpp` and `src/host/*.cpp` automatically, so no manual registration needed there. |
| **Cleanup** (noted while analysing this code) | `src/exec/Host_System.cpp` L17, L83 | Two places cast `ssd_host_interface` to `Host_Interface_NVMe*` purely to call the shared base's `GetType()`. Fragile with a third subtype in play. Worth fixing to avoid the pattern multiplying. |

## 4. Day-by-Day Plan (~18 working days)

### Phase A: Design (Days 1-3)

**Day 1: Register and descriptor design**
Finalize the UTRD-equivalent command-descriptor layout and the doorbell/register addressing scheme (own address block, not aliased onto NVMe's, see the gap analysis above). Decide baseline queue depth: 32 slots, single UTRLDBR bitmap register.

**Day 2: Class skeletons**
Write header-only skeletons for `Host_Interface_UFS`, `Input_Stream_UFS`, `Request_Fetch_Unit_UFS`, and the transport HBA, following the NVMe/SATA pattern. Stub all methods. Confirm it compiles alongside the existing NVMe/SATA code.

**Day 3: Enum adaptation and regression baseline**
Add `UFS` to `HostInterface_Types` and touch all 5+ switch sites with placeholder cases. Run the existing NVMe/SATA configs to confirm no regression before any real UFS logic is added. This is the checkpoint to catch a silently skipped switch site early.

### Phase B: Single-queue UTP baseline (Days 4-8)

**Day 4: Command descriptor and doorbell simulation**
Implement the command-descriptor struct and doorbell-ring simulation in `Request_Fetch_Unit_UFS`.

**Day 5: Command fetch to User_Request**
Implement command fetch and parsing into `User_Request` (LBA/length extraction only, per the performance-fidelity scope). Account for UPIU header overhead as a fixed added latency.

**Day 6: Completion path**
Connect the completion path: UTRD write-back, doorbell-clear, interrupt. Reuse `segment_user_request` and the existing TSU/AMU pipeline unchanged.

**Day 7: Config and transport integration**
Finish XML config parsing (`Host_Interface_Type=UFS`) and the real switch-case logic at all the sites identified in Phase A/Day 3. Connect `PCIe_Root_Complex` dispatch.

**Day 8: First end-to-end run**
Add build-system entries (vcxproj). Run a first smoke test with a synthetic single-queue workload. Sanity-compare timing behavior against the existing SATA single-queue baseline.

### Phase C: MCQ / UFS 4.1 (Days 9-12)

**Day 9: Multi-queue extension**
Extend the single doorbell/queue model to multiple SQ/CQ pairs (up to 32), with per-queue doorbells. Adapt the NVMe multi-queue machinery as the closest reference.

**Day 10: Arbitration**
Add multi-queue arbitration in the TSU. UFS/MCQ has no NVMe-style weighted priority classes, so implement plain per-queue fairness rather than porting NVMe's URGENT/HIGH/MEDIUM/LOW scheme.

**Day 11: HS-Gear 5 timing calibration**
Add HS-Gear 5 bandwidth/latency constants (23.2 Gb/s/lane). Calibrate UPIU/doorbell overhead against published UFS 4.1 latency figures where available.

**Day 12: Validation**
Run the existing `fast18` trace workloads against the UFS 4.1 config. Compare queue-depth scaling behavior against NVMe and SATA baselines. Fix bugs surfaced by the comparison.

### Phase D: UFS 5.0 delta (Days 13-15)

**Day 13: HS-Gear 6 constants**
Add HS-Gear 6 bandwidth constants (~10.8 GB/s effective) as a version/gear config parameter on the same version 4.1 code path. This is as per the sequential-milestone decision above, no new classes are needed.

**Day 14: Scope confirmation**
Confirm no queue-depth/register-layout changes are needed for 5.0 (spec maintains 4.x hardware compatibility). Document link equalization and inline hashing as explicitly out of scope, since neither has timing relevance at this abstraction level.

**Day 15: Validation**
Run a comparison across UFS 4.1 and 5.0 configs. Confirm the bandwidth increase shows up correctly in throughput and latency statistics.

### Phase E: Testing, docs, wrap-up (Days 16-18, +2 day buffer)

**Day 16: Example configs**
Write example XML configs: `ssdconfig-ufs-4.1.xml`, `ssdconfig-ufs-5.0.xml`, following the existing `fast18` config conventions.

**Day 17: Full regression pass**
Confirm existing NVMe/SATA configs produce byte-for-byte identical output to pre-change runs.

**Day 18: Documentation and risk cleanup**
Short README section describing the UFS model, its parameters, and its explicit scope boundaries. Address remaining risk items: the fragile `NVMe*` casts, any silent-fallthrough switches found along the way.

**Days 19-20: Buffer**
Reserved for fixes surfaced during validation and any scope adjustments.

## 5. Open Decision Before Phase B

Confirm before Phase B starts: build the single-queue UTP baseline first (legacy/SDB-mode behavior, Phase B) as a stepping stone, or skip straight to MCQ (Phase C) if legacy single-queue UFS behavior isn't of independent interest for this project. The plan above assumes the former, since it gives an earlier working checkpoint and de-risks the doorbell/UPIU modeling before adding multi-queue arbitration on top.
